## Problem
joust/src/core/demo.ts:955 advances the wave with nextWaveBcd (LDA WAVBCD / ADDA #$01 / DAA, JOUSTRV4.SRC:2001-2004), so demo.wave is a BCD-PACKED byte: 1..9 then 0x10, 0x11 … 0x19, 0x20. tests/wave.test.ts:155 already pins this — 'nextWaveBcd(0x09) BCD not binary -> 0x10'. But demo.ts:959-968 then passes that raw value to waveRowAt, applyWaveDestruction, spawnWaveEnemies, trollSpawnable and seedWaveBudget, and game.ts:347 resolveWaveType does the same — every one of which is documented as taking a 1-based DECIMAL wave (wave.ts:177-185 'The row for a 1-based wave number … Throws for a wave < 1'). BCD and decimal coincide for waves 1-9, so nothing is visibly wrong until the tenth wave; from there they diverge permanently. MEASURED at the tenth wave: waveRowAt(0x10) returns wave 16's row (bounders 0) instead of wave 10's (bounders 8), so the demo materialises the wrong enemy complement, destroys the wrong cliffs, and seeds the wrong pursuit budget — and the error grows (the twentieth wave holds 0x20 = 32). The whole late-game difficulty curve is therefore reading the wrong rows. Two honest fixes and the story should pick one deliberately: (A) keep demo.wave BCD as the ROM's WAVBCD byte is and decode ONCE at each consumer boundary, or (B) hold a decimal wave in DemoState and derive the BCD only where the ROM's byte semantics actually matter (display, the 0x99 wrap). (B) is likely simpler but changes a field every jt2/jt3/jt4 test constructs, so expect a broad re-seat — grep every 'wave:' literal in tests/. NOTE the wrap differs between the two: nextWaveBcd wraps at 100 waves, while waveRowAt loops the TABLE at 81 (WTBRST, :2535) — confirm which the ROM actually does before assuming they must agree. FOUND BY: Reviewer during uf1-2 code review, which was REJECTED for adding a NEW consumer of the same confusion (the per-wave difficulty seam). uf1-2 fixes only its own hop; this story owns the pre-existing consumers. Do this BEFORE uf1-8/uf1-9, which will add more per-wave consumers on top of the same counter. ADDED BY uf1-2 ROUND-2 REVIEW: (a) a THIRD consumer not listed above - the dev overlay. game.ts:613 overlayReadout returns game.wave (the raw BCD byte) behind a doc comment reading 'The 1-based wave', and main.ts:135 prints it, so the overlay shows 'WAVE 16' on the tenth wave. Note the fix points the OTHER way for this one: the ROM PRINTS the BCD digits (WAVEN3 does LDA WAVBCD / BITA #$F0 / BNE / ORA #$F0 / JMP OUTBCD, :2399-2403 - the ORA blank-suppresses the leading zero), so the display wants the byte FORMATTED, not decoded. (b) PRIMARY-SOURCE FINDING that sharpens the choice: WAVBCD has exactly FOUR references in the whole 1982 source - CLR at :1875, the increment at :2001-2004, and ONE read at :2399, which is the display routine. It indexes NOTHING. The wave TABLE is walked by a SEPARATE pointer (LDX PWAVE,U / LEAX WLEN,X / CMPX #WTBEND / LDX #WTBRST, :2011-2019) and the DYTBL difficulty walk by a per-row RAM countdown run from IWAVE at wave-end (:945, :2099). Both are monotone and neither resets. So demo.wave conflates TWO ROM concepts, and option (B) is really 'model PWAVE, derive WAVBCD for display' - which makes (B) the faithful choice, not merely the simpler one. (c) uf1-2 left a TRIPWIRE: stepDemo now calls decimalWaveFromBcd(demo.wave), which THROWS on a non-BCD byte. If this story makes demo.wave decimal, the game dies at the tenth wave (10 = 0x0a) until that call site is updated in the same change. Tests catch it first. (d) uf1-2 could not fix the ROLLOVER and pinned it as a known divergence: from wave 101 the counter reads 0x01 again, so the difficulty RESETS to its wave-1 value and re-climbs, once per hundred waves. A monotone counter removes this; the pinning test in tests/difficulty-wiring.test.ts is expected to fail when it does, and should be updated then.
