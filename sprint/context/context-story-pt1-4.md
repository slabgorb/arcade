## Problem
Playtest 2026-08-19: make the star-wars canvas a fixed size rather than tracking
the window. Prerequisite-ish for pt1-3 (pin the box before pinning the math).

## Findings (research complete)

**Today:** `main.ts:38-49` — canvas fills the window via `@shared/view
resizeToDisplay` on every resize (dpr capped 2); `render(ctx, state, W, H)` in
CSS px; `index.html` has no sizing CSS beyond `canvas { display: block }`.

**The concrete display problem (three seams, one cause):** since sw10-1 the 3D
scene draws into a CENTRED SQUARE of side `min(w,h)` (`wireframe.ts:51-54`,
because the cabinet lens is symmetric ±45° square glass) — but:
1. HUD/attract/select/game-over layers use FULL-WINDOW fractions (`w/2`,
   `h*0.26`, …) — a different box from the scene;
2. `shell/input.ts:20-25` normalises the yoke to the full canvas rect — aim ±1 is
   the window edge while scene NDC ±1 is the square edge; on 16:9, horizontal aim
   is compressed relative to where targets draw;
3. the pointer listener is on `window`, so aim can exceed ±1 (documented open
   sw7-17 follow-up at `render.ts:754-766`).
A fixed square surface collapses all three into one box. (It also fixes half of
pt1-11's select hit-region mess — the third aim→screen map.)

**Fleet convention:** the raster games use fixed logical rasters +
`fitIntegerScale` (wrong for a vector game). The right template is
**battlezone/missile-command's letterbox adapter**: canvas pinned to a target
aspect via `@shared/view letterbox` + `resizeToDisplay`
(`plugins/battlezone/src/shell/viewport.ts:25,75-90`, `main.ts:88-96`;
missile-command `viewport.ts:52` `TARGET_ASPECT = 256/222`). `@shared/view`
already provides everything (`src/shared/view.ts:60 letterbox`, `:165
resizeToDisplay`); its header states the epic rule: share the VERB, keep the
NUMBERS per cabinet. No shared change needed.

**The number: `TARGET_ASPECT = 1` (a square).** Unusually well-determined — the
lens is symmetric ±45° on BOTH axes and aspect-independent (`gameRules.ts:16`,
`render.ts:459-461`, projection audit §2), and the ROM's message field spans
roughly ±512 both axes (`TCMES.MAC` coords; `VGOFFY == -104.` `WSGLOB.MAC:37`).
With `w === h`, `ndcToScreen`'s square IS the canvas, and HUD fractions, yoke
normalisation and scene NDC land in the same box.

## Technical Approach
1. New `plugins/star-wars/src/shell/viewport.ts` wrapping `@shared/view
   letterbox(…, 1)` + `resizeToDisplay` (battlezone shape); wire in `main.ts`
   replacing the bare fill-window resize.
2. Move the pointer listener from `window` to the canvas (closes the ±1 overshoot
   divergence) — or clamp; either way document against the sw7-17 note.
3. Check `docs/ops/shell-adoption-matrix.md:23` / `tests/shell-convergence.test.mjs`
   for a matrix row update (orchestrator suite — node:test, not vitest).
