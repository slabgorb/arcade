# pm3-9 — Authentic maze drives both: rebuild `core/maze.ts` topology from the byte-cited capture

**Story:** pm3-9 (8 pts, p2, `workflow: superpowers`)
**Branch:** `feat/pm3-8-authentic-maze-tilemap` (co-ships pm3-8 + pm3-9 as one deliverable)
**Date:** 2026-08-08
**Predecessor:** pm3-8 (shell-only authentic render; left the branch RED-by-design where its oracle
detects `core != authentic`). This story turns that oracle green by making the core topology authentic.

---

## Problem

The rendered board is malformed. pm3-8 made the *render* authentic (MAME video-RAM capture → tile-index
bake → monochrome-by-cell-type render, orientation candidate B `pacman_scan_rows(sy, 27-sx)`), but the
*core* maze topology is still pm1-3's self-declared "faithful-style reconstruction, NOT byte-cited". The
two genuinely diverge — 68 of 240 dot cells differ, plus corridors, plus the tunnel row sits 3 rows off.
Colour/type come from core, shape from the authentic tilemap; where they disagree the board garbles
(broken blue wall-dashes + stray peach bars — visually confirmed, board upright and correctly coloured
but wrong shape).

**Owner decision (2026-08-07):** the authentic maze must drive **both** render and gameplay. A shell-only
authentic render cannot match a non-authentic core; there must be one source.

## Goal

Rebuild `core/maze.ts`'s per-cell topology (`wall`/`path`/`dot`/`energizer`/`tunnel`/`house`/`gate`)
**from the authentic capture, byte-cited**, so collision + dots + render share one source. When core
matches the capture, the pm3-8 oracle goes green, render and gameplay agree, and the board is correct.

## Verified premise (measured 2026-08-08, before design)

Classifying the scan-ordered `MAZE_TILES` (unpacked from `reference/graphics/maze-vram.bin`) with the
story's classifier yields, over the 36×28 grid:

- **240 dots** (`0x10`) + **4 energizers** (`0x14`) = **244** — matches `pacman.asm:20e6` exactly.
- 596 wall-art tiles (206–253), 168 path (blank `0x40` / `0` / letters 48–90), **zero unclassified**.
- The only **interior** row (3 ≤ y ≤ 32) open (background) at both cols 0 and 27 is **row 17** — the
  authentic tunnel row. The current core reconstruction wraps at row 14. (Rows 0,1,34,35 also read
  open but are HUD/border, excluded by the interior bound.)

The classifier is therefore complete and exact — no fudge factor — and the 244-pellet invariant is
preserved by the authentic layout, not merely assumed.

## Design

### 1. Architecture & data flow

A build-time tool `tools/bake-core-maze.mjs` (sibling to the existing `tools/bake-graphics.mjs`):

1. reads the vendored, citation-gated `reference/graphics/maze-vram.bin`;
2. unpacks it with the **same** `mazeCellOffset` decoder the shell bake uses (`src/shell/gfx-rom.ts`,
   MAME `pacman_v.cpp:170 pacman_scan_rows`) — one decoder, no second copy;
3. applies the classifier and re-derives tunnel/house/gate (§2);
4. emits a **generated** module `src/core/maze-topology.generated.ts` exporting the authentic
   `MAZE_ROWS: readonly string[]` (ASCII, one character per tile, human-readable and diffable), with a
   `GENERATED by tools/bake-core-maze.mjs — do not hand-edit` header mirroring
   `src/shell/maze-tilemap-data.ts`.

`core/maze.ts` imports `MAZE_ROWS` from that generated module in place of the inline pm1-3 table. Its
public API — `tileAt`, `kindOf`, `isWalkable`, `wrapThroughTunnel`, `MAZE`, `TUNNEL_ROW`,
`ENERGIZER_TILES`, `DOT_COUNT` — is **unchanged**. The HUD assembly (`HUD_ROW` bands + spread, §3) and
all load-time guards stay in `maze.ts`.

**Boundaries:** all classification lives in the tool (an `.mjs` outside `src/`, free to use the shell
decoder). Core receives only finished ASCII strings — no shell import enters `core/`, so the purity
sweep (`tests/purity.test.ts`) stays green. The source of truth is the MAME capture, so the GPL firewall
holds: nothing is copied from `shaunlebron/pacman` (read-only reference only).

### 2. Classifier & geometry re-derivation (in the tool)

**Per-cell classifier** (verified complete over the capture):

| Tile index          | Char | Kind        |
|---------------------|------|-------------|
| `0x10` (16)         | `.`  | dot         |
| `0x14` (20)         | `o`  | energizer   |
| 206–253 (wall-art)  | `#`  | wall        |
| `0x40` (64) / `0` / letters 48–90 | ` ` | path |

**Tunnel:** the unique interior row (3 ≤ y ≤ 32) that is background at cols 0 and 27 → row 17. Emit `T`
at both ends of that row. Assert exactly one such row (fail the bake otherwise).

**House + gate:** the GAME OVER banner's letter tiles contaminate the house interior (letters classify
as path), so house and gate are derived **geometrically**, not from tile class:

- Compute the central rectangle enclosed by the house wall-art in the mid-band (rows ~12–22). Its
  interior cells become `H` house — this **overrides** the letter→path classification for those cells.
- The door tiles at the top-centre of that rectangle become `=` gate.
- Guarded by the oracle's "house hollow" sub-test (> 10 interior background cells) plus a bake-time
  assertion that a gate was placed.

### 3. HUD rows & alignment

Rows 0–2 and 33–35 remain synthetic all-`#` HUD bands (as today) — non-playable, and their absence of
dots means the oracle imposes no constraint there. Only playfield rows 3–32 are classified from the
capture. The emitted 36-row grid stays **1:1 row-aligned with `MAZE_TILES`**, which is exactly what the
oracle compares core against (`tileAt(tx,ty)` vs `MAZE_TILES[ty][tx]`).

### 4. Invariants preserved

- `TOTAL_PELLETS = 244` (`pacman.asm:20e6`) with `DOT_COUNT` still **derived** — the authentic layout
  matches, so `maze.ts`'s existing load-time cross-check (table dots == 244 − energizers) holds unchanged.
- pm3-2 tunnel position-wrap survives, now anchored at the authentic `TUNNEL_ROW` (17) — `TUNNEL_ROW` is
  still computed from the table (`findIndex 'T'`), never hardcoded, so the move is automatic.
- Purity sweep; GPL firewall; the `MAZE-VRAM-CAPTURE` citation (added in pm3-8 Task 5, `graphics.json`).

### 5. Testing — definition of done

- **pm3-8 oracle** (`tests/shell/maze-tilemap.test.ts`) goes fully **GREEN**: every core dot cell carries
  `0x10`; the four energizer cells carry `0x14`; exactly four energizer tiles; the tunnel row is
  background edge-to-edge; the house band interior is background (hollow house).
- **New re-derivation test** (`tests/core/`): the generated `MAZE_ROWS` equals a fresh classify-and-
  re-derive over `maze-vram.bin`, so the committed table can never silently drift from the capture
  (the byte-fidelity guard; also the byte-citation of record for the core topology).
- **Re-baseline** coordinate-pinned gameplay tests (`tests/core/targeting.test.ts`, `ghost.test.ts`,
  `pacman.test.ts`, and `game.test.ts` house/mode) to the authentic geometry. Behavioral invariants — 244 pellets,
  tunnel-wrap @ row 17, house hollow, purity, GPL — stay **hard** assertions, never relaxed.
- **Control render + Playwright visual** showing a recognizable authentic maze (per the story's VERIFY
  clause), on its own dev port.
- Full `pac-man` vitest project green; orchestrator suite + citations gate + purity sweep green.

### 6. Risks & mitigations

- **Re-baselining hides a real bug.** The authentic geometry moves corridors, so a gameplay test may
  break because ghost pathing / pac-man movement genuinely changed, not because a coordinate literal is
  stale. Under "authentic is ground truth," investigate each break before re-baselining: a moved-corridor
  change is a truth-fix to accept; an actual regression in `isWalkable`/targeting is a bug to fix. Do not
  paper over a break by loosening an assertion.
- **House/gate geometry ambiguity.** Letter contamination means the house cannot be read from tile class.
  The geometric derivation is guarded by the hollow-house oracle and a gate-present bake assertion; if the
  central-rectangle detection proves ambiguous, fall back to the byte-cited ROM door coordinates with a
  comment, still guarded by the same tests.
- **Generated module under `core/` and purity.** A generated ASCII data module is pure; the tool that
  produces it lives outside `src/`. The purity sweep scans `core/` source text and will pass, but confirm
  the generated file carries no shell import and no clock/DOM/random reference.

## Out of scope

- Any change to the shell render pipeline (pm3-8 delivered it; this story only makes core agree).
- Any change to shared decode / `colourLookup` (the PIVOT in pm3-8 deliberately routed around it).
- MAME input injection for a cleaner capture (proven a dead end in pm3-8 controller research; the attract
  capture already carries the full authentic layout, letters excepted).
